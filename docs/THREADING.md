# Thread ownership and responsiveness

Keyboard and mouse hooks have dedicated message-pump threads. Their high-frequency callbacks must not read WPF dependency properties, invoke the UI synchronously, access files, repeatedly look up processes or perform route/render work. Map mouse suppression uses the foreground PID and the game window handle validated when the map opened. Previously blocked button releases are still paired after focus changes. Ordinary keyboard transitions use the sampled game handle; a watched key arriving at a focus boundary can validate the foreground game before the sampler catches up, preserving chat/input safety.

The WPF dispatcher owns windows, controls, menus, map state, POI cluster caches and icon creation. `Refresh` and retained-POI snapshot preparation verify dispatcher ownership. Native controller UI work shares that application UI thread; background completions post results back to it.

`RenderOverlay` checks and marshals a worker notification before forwarding it to WPF. The WPF branch must not bypass this dispatch step; direct worker calls to `Refresh` still fail fast.

The UI publishes native window handles and text-entry focus as an input-ownership snapshot. Keyboard-hook checks read that snapshot rather than inspecting `WindowInteropHelper`, `Keyboard.FocusedElement` or the live dialog list from their own thread. Window initialization, focus changes and modal stack changes update the snapshot on the dispatcher.

Dense full-map POIs are copied into immutable drawing stamps on the UI thread. Each stamp contains coordinates, sizes and frozen icon/pen assets. A worker builds and freezes a retained drawing from that snapshot. It never reads controls, live clusters, current map state or mutable filters. One shared slot bounds POI construction across surfaces. New requests cancel obsolete work; generation checks reject stale completions. The UI applies a completed drawing through its dispatcher. Camera panning reuses that drawing, and zooming can display a scaled valid layer until the replacement is ready. Small scenes remain inexpensive synchronous drawings. Immutable polygon bounds are cached rather than recalculated on each frame.

Squad route searches remain off the dispatcher with a bounded calculation gate. They run at below-normal priority, restoring the worker's original priority before returning it to the pool. The road router serializes its reusable A* search scratch arrays with `searchLock`; callers do not share mutable search state without that lock. Route revisions discard obsolete results. Only the UI applies navigation state or changes controls.

The same below-normal priority rule applies to dense POI recording. No await occurs between setting and restoring thread priority. Workers do not hold a POI slot while waiting synchronously for the UI.

At ordinary full-map scales the worker rasterizes the frozen POI drawing once into a frozen image, bounded to 4096 pixels per side. It captures the DPI on the dispatcher and never reads the surface from the worker. Larger scales retain vectors to preserve zoom detail without unbounded image allocation. This avoids replaying thousands of icon primitives during composition when only the player or destination changes. Measure complete composition as well as drawing-command recording; a fast `OnRender` alone does not prove responsive presentation.

Changed destination identities bypass the routine refresh and HUD-text throttles. Setting a GPS target does not invalidate unrelated zone/location caches. Road search still runs separately; direct distance and approximate travel time remain visible while it is pending. Multi-stop readouts combine the current leg with the remaining journey on the dispatcher, using only completed immutable route plans or explicitly labelled direct estimates.

Regression verification covers dispatcher misuse, frozen scene publication, repeated full-map redraw timing, menu persistence through refresh, nested actions, input-thread mouse suppression and obsolete route work. Performance measurements must wait for the requested scene to arrive, so a missing layer cannot produce a falsely fast result. Use synthetic profiles; player databases and group credentials are not performance fixtures.

Group state uses a short model lock. Credential changes are serialized separately; DPAPI, durable file replacement and management requests never run under the model lock. The UI reads immutable membership views, and incoming group names are saved by a coalesced worker with observable errors and retries. Router renewal and lease withdrawal run outside UI-facing locks; cleanup remains ordered before a replacement lease is created.

Terrain indices and the overview are prepared at startup. Interactive draws only read the UI cache and enqueue bounded requests. One worker owns detailed tile reads and PNG decoding; only frozen images cross to the dispatcher. The overview remains visible while detail loads. The decoded cache is limited to 128 tiles, with at most 64 visible detail tiles per view and 64 pending requests. High-DPI detail selection steps down a pyramid level when necessary, so a frame cannot evict itself continuously. Closing marks the loader stopped and defers stream disposal until its current read ends, without waiting on the dispatcher.

Label layouts are retained until their camera, filter, language, font or zone inputs change. POI filter changes synchronize existing sidebar switches and counts, preserving focus and scroll state. Input interactions bypass the routine refresh throttle. Settings are assembled into one snapshot before atomic replacement; POI changes use the existing delayed save and shutdown flush.

Camera bursts retain and transform the last completed tactical POI scene and label positions. They do not rebuild clustering, prepare every icon or search hover habitats during movement. One 33 ms render-priority timer requests the next frame using the latest camera state; incoming tile/scene completions share that request. Frozen drawing snapshots are rasterized on one below-normal-priority worker into a frame capped at 1600 pixels on its longest side. There is at most one pending snapshot and one pending completion; newer requests replace older ones. A completed stationary scene prepares one movement frame in advance, without replacing the full-quality idle drawing. The dispatcher composes the last frame at the current camera transform, filling only exposed margins from the terrain overview. Workers never read State or controls. After 200 ms without camera input and once the drag is no longer held, normal sampling and current-zoom layout resume. Filter actions end gesture mode immediately; generation checks reject old frame completions. Actual transparent-window presentation still depends on display size and system load. Verify both camera-command recording and rendered output, and do not equate offscreen timing with in-game FPS.

The tactical renderer retains four DrawingVisual children, in paint order: terrain/grid/habitats, history trail, saved annotations/POIs/labels, and live navigation/players/shared markers/deaths. Static-layer keys include camera, content/filter revisions and the settings that affect that layer. Live state publication updates the live visual without invalidating the parent or reconstructing static drawings. Trail changes update their own visual. Terrain tile notifications increment only the terrain revision. This preserves history under saved zones and navigation above annotations. The compact HUD continues to use the combined drawing path.

Movement-frame workers receive a frozen static composite of terrain/grid/habitats, trail and annotations. The transparent/software path presents that bounded image during camera gestures to avoid replaying dense annotation vectors. Route guidance and player markers remain separate live visuals. Idle presentation and direct retained composition keep all four layers independent. Terrain redraw requests are coalesced, and a completed background is prepared in advance for the next camera gesture. Test builds provide explicit solid/transparent tactical launchers; the solid variant creates a normal opaque window before its HWND exists, retaining the non-activating input policy and a transparent HUD. It does not toggle window transparency on an existing HWND or silently migrate saved settings.

In the solid test mode, a nonzero WPF rendering tier with no forced software-only process mode selects direct retained-terrain composition and does not queue software terrain frames. Tier-zero or forced-software systems retain the bounded worker path. The tier is a capability check, not proof of individual GPU operations. The test-only SCUM_MINIMAP_TAC_RASTER=1 override allows window-transparency and raster-worker costs to be measured separately.

The Fast Tac launcher passes --fast-tac-test on the command line. This selects the test window before HWND creation even when normal startup crosses UAC elevation and caller environment variables are discarded. The environment switch remains available for isolated diagnostic hosts; release builds ignore both selectors.

Once a compatible stationary snapshot is available, transparent/software camera gestures bypass static-layer keys, terrain preparation, annotation recording and replacement raster requests. The dispatcher reprojects that same frozen image and redraws only live guidance. Newly exposed margins use the overview until idle restores detail. Tile completion revisions accumulate for that idle redraw. A held pointer drag prevents the settle timer from restoring expensive detail between slow mouse events; hiding the map cancels the pointer state. The single coalesced frame timer and bounded camera-completion publication run at Render priority so a continuous Input-priority queue cannot postpone them until the gesture has finished.
